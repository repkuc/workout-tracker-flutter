# CLAUDE.md

## 1. Project

**Workout Diary** is a Flutter app for tracking strength workouts. It targets Android and is published on Google Play (`applicationId lv.repkuc.workoutdiary`). All data lives on the device; there is no backend. The UI is in three languages: Russian, Latvian and English.

Code comments are written in Russian. Keep new comments in the same style and at the same density.

## 2. Architecture

```
lib/
  main.dart        – init WorkoutService + exercise migration, EasyLocalization (ru/lv/en), themes
  models/          – plain Dart classes with toJson()/fromJson()
  services/        – data access + business logic; the only layer that touches SharedPreferences
  pages/           – full screens (StatefulWidget), call services directly
  widgets/         – reusable stateful cards (charts, active-workout banner)
assets/
  exercises/exercises.json   – built-in exercise library (trilingual names + muscleGroup)
  exercise_images/           – demo frames <id>_0.webp / <id>_1.webp for all 48 built-in exercises
  translations/{en,ru,lv}.json
  images/muscles/, sounds/ (rest-timer end), icon/
docs/exercise_images/        – SOURCE.txt (licence) + MAPPING.md (source exercise per id); not bundled
```

**Flow:** Page → Service (load the whole list from SharedPreferences, change it, save the whole list back) → Page calls `setState`. Nothing sits between pages and services: no state-management package, no repository layer, no DI.

**Navigation:** `MainPage` has 5 bottom tabs inside an `IndexedStack` that is keyed by `context.locale`, so all tabs rebuild when the language changes:
`HomePage` · `ProgramsPage` · `HistoryPage` · `StatisticsPage` · `SettingsPage`.
`ActiveWorkoutBanner` sits above the `NavigationBar`. Other screens open through `Navigator.push(MaterialPageRoute(...))`; named routes are not used.

`StatisticsPage` has 3 inner tabs: `_OverviewTab`, `ProgressPage` (charts), `BodyMeasurementsPage`.

### Models (`lib/models/`)
- `workout_models.dart`: `Workout` → `List<Exercise>` → `List<WorkoutSet>`.
  - `Workout.status` is `'draft'` or `'done'`. Dates are `'YYYY-MM-DD'` strings. Timestamps (`startedAt`, `finishedAt`, `pausedAt`) are ISO-8601 strings.
  - Timer fields: `startedAt`, `pausedAt`, `totalPausedSeconds`, `duration` (seconds, computed on finish with pauses subtracted).
  - `copiedFromWorkoutId` / `Exercise.copiedFromExerciseId` link a workout to the one it was copied from. They drive the "before / after" comparison in the editor.
  - Program link: `programId`, `programWorkoutId` (the `ProgramWorkout.id` of the day), `programWorkoutName`, `programName`. `programName` / `programWorkoutName` are **snapshots** taken at creation, so the badge still shows correctly if the program or day is later renamed or deleted. See Key patterns → Program day link.
  - Exercise plan (goal): `Exercise.plannedSets`, `plannedRepsMin`, `plannedRepsMax` (all nullable). Copied from the program day as a **snapshot** by Start / Repeat; later program edits don't change existing workouts. Null for manually added exercises, non-program workouts and History → Repeat copies (`copyWorkout` doesn't copy plans). `hasPlan` = `plannedSets != null`; `doneSetsCount` = sets with `isDone`.
  - `color` (hex string) and `muscleGroups` (keys such as `chest`).
  - Exercise template link: `Exercise.templateId` (built-in `chest_1` or custom `custom_…` / `migrated_…`) and `Exercise.muscleGroup` (key such as `chest`), both nullable, filled by the exercise-ID migration. `name` and `targetMuscle` stay as stored **snapshots** / fallback and are never rewritten. Screens and stats don't use the new fields yet (exercise-ID steps 3–5).
- `program_models.dart`: `TrainingProgram` → `List<ProgramWorkout>` (days) → `List<ProgramExercise>`. These are templates only: no weights.
  - `TrainingProgram`: `name`, `description` (multi-line, may be empty), `scheduleDays` (`List<int>`, weekdays 1 = Mon … 7 = Sun, sorted, may be empty), `isCustom`. The old free-text `schedule` field is gone (see Key patterns → Program schedule migration).
  - `ProgramExercise`: `name`, `targetMuscle` key, `targetSets`, `repsMin` / `repsMax` (`int?`, both null = no reps plan; otherwise 1 ≤ min ≤ max ≤ 100). `normalizeRepsRange()` enforces the rule (only one filled → used for both, min > max → max = min, out of range → clamped / cleared) and runs in `fromJson` and when a day dialog saves. `repsRangeText` → `"8–12"`, `"10"` or null. `copy()` is used by the day dialogs so Cancel leaves the original untouched (it copies `templateId`). `templateId` (nullable) links to the library template, filled by the exercise-ID migration.
- `exercise_template.dart`: library entry with `nameRu/nameLv/nameEn`, `muscleGroup`, `isCustom`, and `getName(languageCode)`.
- `body_weight_entry.dart`: `{date, weight}`.
- `body_measurement_entry.dart`: date plus nullable neck/shoulders/chest/waist/hips/bicep/forearm/thigh/calf, and `getByKey(key)` for the chart chips.

### Services (`lib/services/`)
| Service | Storage key | Notes |
|---|---|---|
| `WorkoutService` | `wt.workouts.v1` (one JSON string), `wt.currentWorkoutId.v1` | Singleton. Caches `SharedPreferences`. Exposes `ValueNotifier<int> dataChanged`, which is bumped on every `saveAllWorkouts`. Handles CRUD for workouts, exercises and sets; timer start/pause/resume; finish; `copyWorkout`; and stats queries (`getVolumeByDateWithName`, `getExerciseProgressByDate`, `getTopExercises`, `getPersonalRecords`, `getLastWorkoutForProgramDay`). |
| `ProgramService` | `wt.programs.v1` | Singleton. CRUD for programs and program days. `createProgram` / `updateProgramMeta` take `name`, `description`, `scheduleDays`. No change notifier. |
| `ExerciseLibraryService` | `wt.custom_exercises.v1`, `wt.exercises_migrated.v1` | Singleton. Built-in exercises are read from assets and custom ones from prefs. `searchExercises(query, lang, muscleGroup:)`. `migrateExistingExercises()` runs **once** at startup and copies exercise names from history into the custom library (compares normalised names in all three languages; it used to compare only `nameRu`, which created custom copies of built-ins). `saveCustomExercises(list)` writes the whole custom list. Adding / saving custom exercises reloads `ExerciseCatalogService`. Valid groups: `ExerciseLibraryService.validGroups` = `chest, back, legs, shoulders, arms, abs`. |
| `ExerciseCatalogService` | none (memory) | Singleton. `init()` awaited in `main.dart`, `reload()` after custom-library changes. Maps id → template and normalised name → id for all three built-in names and custom names; **built-in wins** on a name collision. `normalize(name)`: trim, collapse inner whitespace, lowercase, `ё` → `е` (no fuzzy matching). Helpers for later steps (not used on screens yet): `displayName(templateId:, name:, languageCode:)` (built-in → current language, custom → own name, unknown → stored name), `identityKey(templateId:, name:)` (`templateId`, else id found by name, else `name:<normalised>`), `isBuiltInDuplicate(template)` (custom named like a built-in → hidden in the exercise picker). |
| `CustomExerciseService` | none (works through the other services) | Singleton. Backs the My exercises screen: `loadEntries()` (custom exercises + `ExerciseUsage` {workouts, programs}, most used first; also **deletes unused custom duplicates of built-ins** from the library, used ones stay hidden and are not listed), `usageOf(id)`, `merge(sourceId:, target:, languageCode:)`, `renameConflict(id, name)` (`'empty'`, the id of a built-in / other custom with that normalised name, or null), `rename(id, name)`, `setMuscleGroup(id, group)`, `delete(id)` (false if used). See Key patterns → My exercises. |
| `ExerciseIdMigration` | `wt.exercise_ids_migrated.v1`, `wt.exercise_ids_migration_summary.v1`, pre-migration copies | Singleton. `run({force})`, see Key patterns → Exercise-ID migration. |
| `BodyWeightService` | `body_weight_entries` (a `StringList` of JSON strings) | **Not** a singleton, and an older storage format. One entry per date (upsert), kept sorted in ascending order. |
| `BodyMeasurementService` | `wt.bodyMeasurements.v1` | Singleton. One entry per date (upsert). Sorted newest first. |
| `ExerciseImageService` | none (assets) | Singleton. `init()` is awaited in `main.dart` (built-in templates + `AssetManifest`; only ids with both frames count). `findTemplate(id:, name:)` / `imagePaths(id:, name:)` → `[start, end]` or null. Looks up by template id first, then by name (trimmed, case-insensitive) against `nameRu` / `nameLv` / `nameEn`. Custom exercises → null. |
| `BackupService` | none | Export: a JSON map `{workouts, bodyWeight, bodyMeasurements, programs, customExercises}` (`buildExportJson()`) is written to the temp dir and shared via `share_plus`. Import: `file_picker` → `importDecoded()`. A bare List (the legacy workouts-only format) is also accepted. `customExercises` (custom library only, never built-ins) is imported **first**, merged **by id**: new id → added (always `isCustom: true`); same id + same names → skipped; same id + different name → local kept, imported skipped, counted in `skippedCustomExerciseConflicts` (not shown in the UI: the import snackbar only shows the workout count). Imported entries with a built-in id are ignored; old backups without the key import as before. Workouts and programs merge **by id** (existing ones are skipped, never replaced). Weight and measurements merge **by date** (upsert). Returns the number of imported workouts. |

## 3. Key patterns

- **Singleton services:** `static final _instance = X._internal(); factory X() => _instance;`. `WorkoutService()` can be called anywhere and returns the same object. (`BodyWeightService` and `BackupService` are not singletons; `BackupService` only keeps `skippedCustomExerciseConflicts` from its last import.)
- **Storage = SharedPreferences + JSON.** Each collection is a single JSON string under a versioned key `wt.<name>.v1`. Every mutation follows the same steps: `loadAll` → find by `indexWhere` → mutate → `saveAll`. Methods return `bool` (false = not found).
- **JSON serialization:** written by hand as `toJson()` / `factory fromJson()`. `fromJson` must stay **backward compatible**: new fields need `?? default` or must be nullable, because old saved data and old backups do not contain them. Numbers are read as `(json['x'] as num).toDouble()`.
- **Backup compatibility:** a new data collection needs a new top-level key in the export, and import must null-check it, so old backups still import and old app versions ignore the new key. New fields inside an existing collection need no backup change: export and import go through `toJson` / `fromJson` (e.g. programs' `description`, `scheduleDays`, `repsMin` / `repsMax`; an old backup without them gets the defaults plus the schedule migration).
- **Program schedule migration:** older versions stored a free-text `schedule` on `TrainingProgram`. `TrainingProgram.fromJson` moves a non-empty `schedule` to the **start** of `description` (schedule text, an empty line, then the old description, or just the schedule if the description was empty) and leaves `scheduleDays` empty; `toJson` no longer writes `schedule`. Idempotent: each read of old data gives the same result, and the first save of the programs list (any program edit, import) stores the migrated form. Old backups go through the same `fromJson`.
- **Program day link (by id, name fallback):** workouts created by Start / Repeat store `programWorkoutId`. `WorkoutService.getLastWorkoutForProgramDay(programId, dayId:, dayName:)` (used for "Last done" and as Repeat's source workout) matches `programId` plus: the day id when the workout has one, otherwise (old workouts) the day **name** as before. When a day is edited in Program details, `linkOldWorkoutsToProgramDay` first stamps the day id onto old workouts found by the day's current name, so a rename keeps their history too. Program details keys `_lastWorkoutsByDay` by day id. A deleted and re-created day gets a new id and does not inherit the old day's history.
- **Exercise goal on cards:** `lib/widgets/exercise_goal.dart` — `exerciseGoalText(exercise)` → `"4 × 8–12"`, `"4 × 10"` (from = to) or `"4 sets"` (`programs.sets_short`, no reps plan), null without a plan; `ExerciseGoalLine(exercise:)` → `🎯 goal` (accent) + counter `done / planned` (`inactive`; `✓ done / planned` in `success` once done ≥ planned). Editor: `ExpansionTile.subtitle` under the name (indented 24 to line up with it), only when `hasPlan`, so cards without a plan are unchanged. Workout details: under name / muscle. Semantics labels `workout.goal`, `workout.sets_done`. Sets are never pre-created from the plan.
- **Program weekdays and reps plan UI:** `lib/widgets/weekday_selector.dart` has `WeekdaySelector` (7 toggle chips Mon … Sun, one row when they fit at ≥ 36dp each, otherwise wrap at 44dp; `unselectedColor` = `inputFill` in dialogs, `inputFillOnPage` on a page; needs a fixed width inside `AlertDialog`, i.e. `SizedBox(width: double.maxFinite)`, because it uses `LayoutBuilder`) and `formatScheduleDays(days)` → `"Пн · Ср · Пт"`, all 7 → `programs.every_day`, none → `''`. Short names: `programs.weekday_short_1…7`. `lib/widgets/exercise_plan_editor.dart` has `ExercisePlanEditor(exercise:)`: a column `Sets [−][3][+]`, a small heading `Reps` with a thin line, then `from [−][field][+]` and `to [−][field][+]` (shared `StepButton`; keys `programs.sets_label`, `reps_label`, `reps_from`, `reps_to`). Labels share one right-aligned column as wide as the longest label (measured with the phone's text scale, max 96dp), always one line (`FittedBox` scales down instead of wrapping). Sets: 1–10, buttons only (not typeable), new exercises start at 3. Reps fields: digits only, max 3 chars. It writes straight into the exercise copy. Empty "from" + → 8; empty "to" + → "from" (or 12); − at 1 clears the field; "from" above "to" pulls "to" up; "to" can't step below "from". New program exercises start with no reps plan. The add/edit day dialogs (Create program and Program details) use `insetPadding` 16 horizontal for room, and each exercise row is name (+ ⓘ, ✕) on the first line, the plan editor below. Displays: `"4 × 8–12"` / `"3 × 10"` with a plan, otherwise `"4 sets"` (Program details expanded day, Create program view-day dialog).
- **Screen refresh:**
  - Pages that show workouts (`HomePage`, `HistoryPage`, `ActiveWorkoutBanner`) subscribe to `WorkoutService().dataChanged` in `initState` and unsubscribe in `dispose`.
  - After pushing a screen that can change data, reload with `Navigator.push(...).then((_) => _load())` or with `await Navigator.push(...); _load();`. **This is the reliable way.**
  - `ProgramsPage` and `ProgramDetailsPage` also call `_load…()` from `didChangeDependencies()`. Don't rely on that alone: it runs after `initState` and when inherited widgets change (for example the locale), **not** on a normal `Navigator.pop()`. The comment in `program_details_page.dart:759` already notes this.
  - Check `if (mounted)` after `await` before calling `setState` or using `context`.
- **Localization:** all UI text goes through `'section.key'.tr()` (easy_localization). Add every new key to **all three** files `assets/translations/{en,ru,lv}.json`. Muscle names use the keys `workout.muscle_<group>`.
- **Exercise-ID migration** (`lib/services/exercise_id_migration.dart`): runs at startup after `migrateExistingExercises` and `ExerciseCatalogService().init()` (skipped once `wt.exercise_ids_migrated.v1` is set; a failure is caught, so the flag stays unset and it retries next start) and with `force: true` after every backup import. Steps:
  1. Once only (guarded by the workouts copy key), the raw strings of `wt.workouts.v1`, `wt.programs.v1`, `wt.custom_exercises.v1` are saved to `wt.workouts.pre_id_migration.v1`, `wt.programs.pre_id_migration.v1`, `wt.custom_exercises.pre_id_migration.v1` for manual recovery. Later runs never overwrite them.
  2. Every workout exercise and program exercise with a null `templateId` gets one: built-in name in any language → built-in id (custom duplicates of built-ins map to the built-in); else custom name → custom id; else **one** new custom entry per distinct normalised name (`custom_<millis>_<n>`, name = stored name trimmed, no group). Empty names are left alone.
  3. Workout exercise `muscleGroup` (only if null): the template's group, else the stored `targetMuscle` text reverse-looked-up against `workout.muscle_<group>` in all three translation files (6 valid groups); free text → stays null.
  4. Custom entries with an empty group get the most common `muscleGroup` of the workout exercises using them, only without a tie; then exercises of those customs with a null group get it.
  5. Save: custom library, then workouts, then programs (only what changed), reload the catalog, store the summary JSON (`matchedBuiltIn`, `matchedCustom`, `createdCustom`, `exerciseMuscleFilled`, `customMuscleFilled` — counted per exercise occurrence in this run; `duplicatesHidden` = custom entries currently hidden as built-in duplicates), `debugPrint` it, set the flag last.
  Only null fields are filled, so a rerun changes nothing. Nothing is deleted and names are never rewritten; typos and different wordings stay custom (fixed later in step 2b). The summary key holds the **latest** run (an import overwrites the startup one).
- **Exercise picker result:** `ExercisePickerPage` pops a `PickedExercise(template, alreadyInLibrary:)`, not a bare template. `alreadyInLibrary` = the user typed a name that is already in the library (built-in in any language or an existing custom), so the picker returned that one instead of creating a duplicate. The **caller** shows `workout.exercise_already_in_library` (`alreadyInLibraryText(context, template)`): the editor shows it as its only snackbar (instead of "… added!"), the add/edit day dialogs show it as a muted ⓘ line above "Add exercise" (a snackbar would sit behind the dialog). Optional params: `title`, `excludeId` (hide one exercise), `allowAddCustom` (hide the add-custom button); the merge flow uses all three.
- **My exercises** (`lib/pages/my_exercises_page.dart`, Settings → Exercises): lists custom exercises (name, translated group or "—", `Workouts: N · Programs: M` / "Not used"; a workout or program counts once however many times it holds the exercise). Tap → `AppBottomSheet` with: **Merge into…** (picker without itself and without add-custom → confirm `AppDialog`) — every workout and program exercise with the source `templateId` gets the target id, the target's name in the current language, and the target's group (workout `muscleGroup` + translated `targetMuscle`, program `targetMuscle` key; if the target has no group the old one is kept); then the source is deleted from the library. **Rename** — inline errors: empty, or the name normalises to a built-in / another custom ("use Merge"); renaming to its own name with different case is allowed; writes all three library names and the name snapshots of its workout and program exercises. **Change muscle group** — 6 groups; library entry, workout `muscleGroup` + `targetMuscle` text, program `targetMuscle` key. **Delete** — only when unused (disabled with a hint otherwise), with a red confirm dialog. **Merge and rename are the only places that rewrite stored name snapshots**, on purpose, as explicit user actions; nothing else may. A workout may end up with the same exercise twice after a merge; that is allowed. Refresh: workout saves bump `dataChanged`, which Home, History, the banner and now also Statistics overview, `VolumeChartCard` and `ExerciseProgressCard` listen to; the picker and program screens reload when opened.
- **Muscle values differ by layer:** program templates store muscle *keys* (`chest`). When a workout is created from a template, `Exercise.targetMuscle` gets the *translated text* (`'workout.muscle_chest'.tr()`).
- **Every new workout / program exercise must carry `templateId`** (workout exercises also `muscleGroup`), alongside the `name` / `targetMuscle` snapshot. Creation paths: editor add from picker (`template.id`, `template.muscleGroup`), Create program and Program details day dialogs (`templateId: template.id`), Start / Repeat in Program details (`_templateIdOf` = program `templateId`, else catalog name lookup; `_muscleGroupOf` = program key, else template group), `WorkoutService.copyWorkout` (copies both), `ProgramExercise.copy()`. Any new path must do the same. Program Repeat finds last time's sets by `ExerciseCatalogService.identityKey` (id, else id from the name in any language, else normalised name), so a day built in another language still pre-fills.
- **Exercise identity in history and stats is still the exercise name string** (until exercise-ID step 5), not an id. Progress charts, PRs, top exercises and demo images compare by `name`. **Exercises inside a workout cannot be renamed or edited on purpose** (the editor's pencil / "Edit exercise" dialog and `WorkoutService.updateExercise` were removed): a rename silently breaks those links. Do not re-add it, for built-in or custom exercises. (Renaming a *custom library entry* in My exercises is different: it rewrites every snapshot with that `templateId` at once, so nothing is split.) Old workouts whose exercise names were edited earlier stay as they are. The pencil next to the *workout* name (rename workout) is a separate feature and stays.
- **Draft workout:** at most one current draft, tracked by `wt.currentWorkoutId.v1`. `createWorkout` and `copyWorkout` set it; `finishWorkout` and `deleteWorkout` clear it.
- **Styling:** UI colours live in `lib/theme/app_colors.dart` (`abstract final class AppColors`, `static const Color`). New code must use `AppColors.x` instead of hardcoded `Color(0xFF…)` values. Colours are named by meaning, not shade (`background`, `surface`, `accent`, `success`, `volume`, `textMuted`…), so two roles can share a hex but still be separate constants. Not in `AppColors` on purpose: the user-pickable workout palette and the lists that must match it (`home_page.dart` picker + `_workoutColors`, `history_page.dart`, `volume_chart_card.dart`), and chart series lists (`exercise_progress_card.dart`, `body_measurements_page.dart`). Only `Colors.white` / `black` / `transparent` are still used directly; red and greys are `AppColors.danger` (`EF4444`) / `inactive` / `iconNeutral` (`94A3B8`) / `completedButton` / `snackbarNeutral` (`475569`). The app is dark-only (`0F172A` background, `1E293B` cards, `F97316` accent): `main.dart` has a single dark `theme` with `themeMode: ThemeMode.dark`, light status-bar icons are forced via `AnnotatedRegion<SystemUiOverlayStyle>` in `MaterialApp.builder`, and Android `values/styles.xml` uses the same dark native theme as `values-night`. A text field must contrast with what it sits on: inside dialogs and cards (`surface` `1E293B`) use `inputFill` (`0F172A`); directly on a page background (`0F172A`) use `inputFillOnPage` (`1E293B`) — Create program fields, exercise picker search box. Pages build their own header instead of using an `AppBar`. UI is split into `_buildX()` methods inside one State class, so the files are large (`workout_editor_page.dart` is about 2,650 lines).
- **Headers:** new main tabs must use `TabHeader` (`lib/widgets/tab_header.dart`: orange icon box + 22pt title; `icon`, `title`, optional `trailing`, `bottomPadding`). New sub-pages must use `PageHeader` (`lib/widgets/page_header.dart`: 48×48 back `IconButton` + 20pt one-line title; optional `subtitle`, `trailing`, `bottom`, `showDivider`, `onBack`). Back defaults to `Navigator.pop(context)`; pass `onBack` if the page must pop with a result, confirm or save. Exceptions kept on purpose: `HomePage` (22px icon, own layout around the calendar) and `WorkoutEditorPage` (compact header with timer, pause and rest timer).
- **Dialogs:** new dialogs should use `lib/widgets/app_dialog.dart`: `AppDialog` (15pt title with optional 20px icon, compact 16/14 paddings, 1px border — `borderColor` red for delete, green for finish — content always scrollable), `AppDialogCancelButton` / `AppDialogConfirmButton` (13pt, optional `color`), and `appDialogInputDecoration(labelText, hintText, icon, errorText)`. Show validation errors as `errorText` under the field (via `StatefulBuilder`, cleared in `onChanged`), never as a snackbar: it is drawn behind the dialog backdrop. Every dialog text field has a visible `labelText` (small orange label). Used by all dialogs except History / Workout details (repeat, delete workout).
- **Set dialog (Add set / Edit set):** both built by `_showSetFormDialog` in `workout_editor_page.dart`; each field is a row `[ − ] [ field ] [ + ]` (`_buildSetStepperRow` + `StepButton` from `lib/widgets/step_button.dart`: 40×40 visual, 48×48 touch target, tap = one step, long-press repeats and speeds up from 300 ms to 60 ms, `HapticFeedback.selectionClick()` on every step that changes the value, `Semantics` label `workout.decrease` / `workout.increase`). Reps: step 1, min 1. Weight: step 2.5 kg, min 0 (clamped, bodyweight exercises). Empty field: + starts at the step (1 / 2.5), − does nothing. Typed values stay allowed and the step is added to them (19.2 + 2.5 = 21.7). Weight is parsed with `_parseWeight` (accepts "." and ",") and shown with `_formatWeight` (rounded to 2 decimals, no trailing ".0"). Typing or stepping clears that field's `errorText`. **Add set pre-fills reps and weight from the exercise's last set** in the current workout (empty if it has none); Edit set shows the set's own values. **Set dialogs must not use `autofocus`**: the keyboard opens only when the user taps a field.
- **Snackbars:** `main.dart` `snackBarTheme` makes every `SnackBar` floating with 10px rounded corners (default colour `snackbarNeutral`). Pass `backgroundColor` by meaning: `AppColors.success` for success, `AppColors.danger` for errors only, `AppColors.snackbarNeutral` for neutral confirmations such as "deleted". In `WorkoutEditorPage` add `margin: _snackBarMargin()` so the message sits above the bottom buttons (not for the "workout finished" one, which is shown after the editor closes). Error messages use `'${'workout.error'.tr()}: $e'`.
- **Exercise demo images:** `assets/exercise_images/<id>_0.webp` (start position) and `<id>_1.webp` (end position), where `<id>` is the id in `exercises.json` (`chest_1`, `back_4`…). Source: free-exercise-db (The Unlicense, public domain), credited in Settings → About (`settings.exercise_photos_credit`); max 400px, mostly landscape (`back_8` is portrait). A new built-in exercise needs both frames, otherwise it simply gets no ⓘ. `lib/widgets/exercise_info_button.dart` has the shared UI: `ExerciseInfoButton(templateId:, name:)` is an 18px ⓘ `IconButton` with a 40×40 touch target that renders nothing when the exercise has no images, and its tap does not reach the parent's `onTap` / `ExpansionTile`. `showExerciseDemoSheet(context, template)` opens an `AppBottomSheet` with the name in the current language, the muscle group and the two frames alternating every 0.6 s (150 ms crossfade, both frames precached, rounded corners, real aspect ratio; the timer stops on close). **Rule: every new screen or list that shows an exercise must add `ExerciseInfoButton`** (pass `templateId` when an `ExerciseTemplate` is at hand, otherwise `name`). Skipped on purpose: the exercise chips on the progress chart (too small, and a tap toggles the chart line).
- **Bottom sheets:** use `showAppBottomSheet(context:, builder: (context) => [...])` from `lib/widgets/app_bottom_sheet.dart` (surface background, 20px top radius, drag handle, bottom spacing, content scrolls when taller than the sheet's default max height of 9/16 of the screen, so don't put `Expanded` directly in the list) with an `AppSheetHeader(leading, title, bottom)` (15pt title, `divider` line) followed by `ListTile` actions or 16px-padded content.
- IDs come from `uuid` v4. Custom exercises use the id format `custom_<millis>`.

## 4. Features

- **Home** (`home_page.dart`): month calendar with days coloured by workout (tap a day for a bottom sheet to view, edit or repeat that workout); stats row; body-weight quick entry; "Start workout" dialog (name, colour, muscle groups); program badge.
- **Workout editor** (`workout_editor_page.dart`): add exercises from the picker (exercises themselves are not editable, see Key patterns); add, edit and delete sets (reps × weight, with − / + steppers); mark sets and exercises done; workout timer with pause/resume; rest timer with preset chips, vibration and sound (`vibration`, `audioplayers`); rename; finish dialog that warns about incomplete exercises and compares volume and duration with the source workout.
- **Active workout banner** (`widgets/active_workout_banner.dart`): shows the running draft with a live timer above the bottom nav. Tap it to return to the editor.
- **History** (`history_page.dart`): list of workouts with stats and a program badge. A draft opens the editor; a finished workout opens `WorkoutDetailsPage` (read-only, with repeat). Actions: repeat/copy, delete.
- **Statistics** (`statistics_page.dart`):
  - Overview: period filter, totals, top exercises, personal records.
  - Charts (`progress_page.dart`): `VolumeChartCard`, `ExerciseProgressCard` (max weight per exercise over time), `BodyWeightChartCard`, all built with `fl_chart`.
  - Body measurements (`body_measurements_page.dart`): add, edit and delete entries per date, plus a line chart with a chip for each measurement.
- **Exercise library** (`exercise_picker_page.dart`): built-in trilingual list plus custom exercises; search and muscle-group filter; add a custom exercise. It returns a `PickedExercise` through `Navigator.pop` (a new custom exercise is returned with its real id). "Add custom exercise" never creates a duplicate: a name that normalises to a built-in (any language) or an existing custom returns that one with `alreadyInLibrary: true`, and the caller shows `workout.exercise_already_in_library` ("… already in the library: {name}", built-in name in the current language; see Key patterns → Exercise picker result). Custom duplicates of built-ins are hidden from the list.
- **Exercise demos:** an ⓘ next to built-in exercises on every screen that lists them opens a sheet with a two-frame animation of the movement.
- **Training programs** (`programs_page.dart`, `create_program_page.dart`, `program_details_page.dart`): create a program with weekday chips, a description and workout days with exercises (sets + optional reps range); edit meta (name, weekdays, description); add or remove days; delete. Program list cards and the Program details header show the weekdays; the details page shows the description collapsed to 2 lines with "Show more / Show less". "Start" a day creates a workout from the template. "Repeat" uses the *current* template exercises and pre-fills sets from the last workout of that day, matched by exercise name. Each day shows the date it was last done.
- **My exercises** (`my_exercises_page.dart`, from Settings): manage custom exercises — merge into another exercise, rename, change muscle group, delete unused ones (see Key patterns → My exercises).
- **Settings** (`settings_page.dart`): language (ru/lv/en via `context.setLocale`), My exercises, export/import backup, donate link, app version (`package_info_plus`), privacy policy link (`url_launcher`).
